校务智理｜DeepSeek 原生联网搜索增强版 v2

本版联网能力严格限定为 DeepSeek 官方 API，不使用 Tavily、Bing、Google、DuckDuckGo 或其他第三方搜索服务。

增强内容
1. 使用 DeepSeek 官方 Search API：POST https://api.deepseek.com/v1/tools/search，单次最多取 10 条结果，并请求可用的正文内容。
2. 搜索词不再只截取原问题：自动生成原问题、清理口语/疑问词后的检索词；校务问题额外执行 xawl.edu.cn 定向搜索，最多 3 组查询。
3. 合并多组搜索结果并按相关性评分排序，权威等级只作为次级排序信号，尽量避免只因站点权威而让无关结果排到前面。
4. 对高相关且搜索 API 没有提供足够正文的前两条结果，尝试调用 DeepSeek 官方 Fetch API：POST https://api.deepseek.com/v1/tools/fetch，抓取网页 Markdown 正文供模型判断；抓取失败时仍保留搜索摘要，不会让整个回答失败。
5. 把来源标题、原始 URL、正文/摘要、日期、相关性分数和权威等级一起传给模型，要求模型判断相关性、优先一手来源、处理冲突，并且不能伪造来源或假装搜索成功。
6. 保留之前的真实链接引用规则：没有具体原始链接的内置正文不作为外网引用；不把学校首页或栏目页伪装成文件原文。

部署步骤
1. 备份当前线上 Worker 与前端文件。
2. 将本目录的 index.html、style.css、app.js、config.js 部署到前端静态站点。
3. 将本目录 workes.js 部署到 Cloudflare Worker。
4. 保留现有 D1 绑定与 Worker Secrets：DEEPSEEK_API_KEY、JWT_SECRET、ADMIN_PASSWORD 等。
5. 不需要新增任何搜索供应商账号或搜索专用 Key。DEEPSEEK_API_KEY 只放在 Cloudflare Worker Secret，绝不可写入前端文件。
6. 在网站对话中勾选“联网搜索”测试。搜索与抓取都使用 DeepSeek 官方 API；关闭联网搜索时不执行这些搜索调用。

成本与限制
- 多组查询和网页抓取会比单次搜索消耗更多 DeepSeek Search/Fetch 请求额度。具体价格、额度和计费规则以 DeepSeek 官方文档及账户页面为准。

2026-10-31 第三轮：检索算法重写（BM25F 混合检索）+ AI 回答分层
==================================================================

一、为什么改
上一轮的检索是“字面 n-gram 加权”：把问题切成 2~5 字的所有组合，命中就加分。
这套做法能跑通，但有四个结构性毛病，线上表现是“有时候答得很准，有时候莫名答偏”：
1. 长短片段不平等：一段 2000 字的正文天然比 300 字的办事流程命中更多词，于是长文件总赢。
2. 子串重复计分：“学分置换”会被拆成“学分/分置/置换/学分置/分置换/学分置换”六份一起加分。
3. 跨词碎片当关键词：“学需要”“会记”“能保”这类两个词的接缝，在库里只出现一两次，
   却因为“稀有”而拿到很高的权重，是最主要的排序噪声。
4. 文件被切碎后互相稀释：同一份制度命中好几个片段，展示时挤占了其他文件的位置。

二、检索层改成什么样（workes.js）
1. BM25F 打分：k1=1.25、b=0.72，标题字段权重 2.5，做 TF 饱和与文档长度归一——
   长文件不再自动占优，“第十三条”这种短条文也能排上来。
2. 词表三道闸：
   ① 语料闸：库里根本不存在的词直接丢（df=0）；出现在一半以上片段里的泛词也丢。
   ② 边界闸：以功能字（的/了/能/会/要/不/无…）开头或结尾的组合一律丢，专门治跨词碎片。
   ③ 冗余闸：只有“同样合法”的长词才允许覆盖短词（“答辩没过”不再吃掉“答辩”）。
   最后按 idf×词长取前 24 个，保证“答辩”这类短而关键的概念不会被“一次”这类高频词挤掉。
3. 文档级聚合：先决定“该看哪一份文件”，再决定“看这份文件的哪一段”；
   同一份文件多命中几个片段只做有限加成，文件长不等于更相关。
4. 相邻条款补全：命中的是“第八条”，会把第七条/第九条一起带进上下文（适用条件常写在邻条）。
   但补全放在第二轮，一份文件先只占一个名额，避免长文件用掉全部 5 个位置。
5. 排序加成（都在文档级做，权重克制）：
   - 标题聚焦：问题里最有区分度的 3~5 个概念出现在文件名里 → ×1.17~1.36；
     文件名完全不涉及主题、只靠正文顺带提到一句排上来的 → ×0.86（治“问勤工助学却给建档立卡”）。
   - 意图映射：新增 12 组（AI 使用、处分、证书补办、实习、实验、教材、评教、教学事故、
     信息员、竞赛、创新创业、辅导员、调课），按意图给目标文件温和加权。
   - 程序性问题里，/评价指标体系/工作量测算/听课制度/工作规范 这类“教学管理内部用表”降权 0.6，
     /办理流程/办事指南/补办 加权 1.5。
   - 办事指南类片段不再按“扫描件模板”打压质量分（它们是短流程表，不是空表）。

三、相关性判定（决定“库里有 / 没有”）
1. rel（0~1）＝关键概念覆盖率 ×0.66 + BM25 饱和度 ×0.34。
   覆盖率只看“价值最高的 6 个概念”，不看全部 n-gram——否则长问句会被自己稀释。
   分母设下限，只命中一个概念（“校医院在哪”撞上“医院”）拿不到高 rel。
2. 标题证据：问题的主概念在库里有任何一份文件以它命名（或它的二字片段）→ true。
   “勤工助学”有 → 命中有效；“食堂”“校医院”“校园网”“考研自习室”没有 → 判定超纲。
3. 弱命中（rel<0.5 或没有标题证据）时：
   - 不再把库内文件当“最高优先级依据”塞进上下文，改为“只有沾边文件，不要引用其中条款”；
   - 参考文件列表只保留标题确实点中主题的；
   - 校内问题会自动回查学校官网，把答案交给官网内容。
4. 实测：“食堂/校园网/校医院/停车/军训/考研自习室”这类超纲问题现在全部走官网或办理路径，
   不会再拿《公寓文明行为规范》《学生学籍管理规定》硬答。

   - 强：可给条款、数量、时限、办理地点，但必须写明文件名；
   - 中：只给原则与主流程，凡涉及数字/时限/地点/份数，一律注明“以主管部门最新通知为准”；
   - 弱：只回答“找谁、大致怎么走、准备哪类材料”，禁止给条款号、金额、时限、文号。
2. 问题类型识别（时间节点 / 能否是否 / 标准条件 / 办事流程 / 概念解释 / 一般咨询），
   给对应的输出骨架——“转专业什么时候能申请”按时间作答，不再套整套办事流程模板。
3. 依据弱的回答不写缓存：错误口径不会被固化 3 天。
4. meta 新增 confidence 字段，前端在来源区上方显示“依据充分 / 依据有限 / 未找到原文”徽标
   （强依据不打扰，只在中等/弱时提示；手机端自动隐藏长说明）。
5. 追问补全改写：只取上一轮的“主题词”拼进检索词，不再整句拼接，避免上一轮的次要词冲淡当前意图。

2026-10-31 第四轮：AI 用文件内容裁决引用 + 清除面向用户的元话语
==================================================================

一、这一轮解决的两个问题
1. “链接挂上了，但回答里没用到它”。
   上一轮的引用依据是后端算出来的相似度：一份文件只要字面沾得上就可能被挂到回答下面。
   典型例子是学生问“处分会记入档案吗”，《国家奖学金评审办法》里顺带写了“受处分者不得参评”，
   字面分数够高，于是这份办法也被列成“参考文件”——但学生点开它，找不到自己想要的答案。
2. “回答末尾多出一句解释链接真伪的话”。
   模型偶尔会把系统约束复述给用户，例如“（注：以上链接均可直接打开，不存在伪造链接）”
   “以上链接均来自学校官网，未使用虚构来源”。这类话对办事没有任何帮助，还会让学生反过来
   怀疑内容本身；而且它出现在回答正文里，属于完全不该被用户看到的东西。

二、AI 用文件内容裁决“引不引”（workes.js 新增 judgeEvidence）
1. 时机：在生成回答之前，把候选文件（按文件名归并后，最多 4 份）连同正文片段送给模型，
   让它逐份判断“这段正文里有没有能直接回答问题的实体信息”——具体条款、数字额度、时限、
   适用条件、办理部门、步骤或材料名称。答不上的文件不进入上下文，也不进入来源区。
2. 粒度是“文件”，不是“片段”：同一份办法常命中好几段，若分别送审会出现 A1=是、A4=否 的
   自相矛盾，还会让这份文件在该出现的地方漏掉一半依据。所以先按文件名归并，一份只判一次，
   判定结果再映射回它的所有片段。
3. 输出格式极简（A1=是 / A2=否，max_tokens=60，temperature=0），解析只认这个格式；
   格式跑偏、超时（2.6s）、上游 5xx 一律返回 null，调用方沿用原排序——
   裁决是增强项，不能变成新的故障点。
4. 全判否时保留最相关的一条：宁可多给一条，也不让学生在毫无依据的情况下看到一段“无源”回答。
5. 与联网检索并行：学生手动开联网时，检索和裁决会同时发生，串起来会白白多等一次往返。
   现在先发起裁决、等检索结束再收结果，实测总耗时 277ms（≈ max(250, 240)）而不是 490ms。
6. 只在“库内命中且候选按文件去重后 ≥2 份”时才触发，单一候选直接跳过，省一次往返。
7. 调试：请求体带 debug:true 时，meta.debug.evidence 会给出 candidates / kept / dropped（被裁掉的文件名）。

三、提示词重写：把“不要……”改成正向表述（workes.js）
1. 原来的【联网检索使用规则】【表达节制】里有 8 处否定式元指令，例如
   “不要解释为什么不用”“不要在回答里说明搜到的信息不相关”“不要描述检索与匹配过程”。
   否定指令本身就在反复提示模型“你在做检索、你在筛选链接”，模型很容易把这种自我校正复述出来，
   这正是第二类问题的根源。现在全部改成正向表述：
   - “用户看到的每一句，都应当是他能直接用的东西：结论、该做的事、注意事项。”
   - “同一个意思说一遍就够，后面的段落直接给新的信息。”
2. 把“编造/虚构”这类会触发联想的词也替换掉：“不虚构”→“只写有依据的内容”，
   “不得编造未出现的细节”→“细节以原文为限”。整个 system 里已不含伪造、编造、虚构、捏造。
3. 【标准回答结构模板】末尾那句“（说明：以上模块中关于未收录的提示只在开头出现一次……）”
   属于写给模型的元说明，已删除。
4. 上下文括注（弱命中、自动回查官网、无可用网页）同步改为陈述句，不再携带否定式要求。

四、元话语兜底清理（workes.js + app.js 各一份，行为一致）
1. stripMetaTalk()：两道处理
   ① 括注式元说明——只有当括号里谈的是链接/来源/检索/伪造时才整段去掉；
      “（注：报到时需带录取通知书）”这类有用信息原样保留。
   ② 整句删除——逐句检查，句子只谈“链接真伪/检索过程”就整句丢掉，共 8 条规则
      （以上/以下链接均可打开、链接均来自官网、未使用虚构来源、检索过程已省略……）。
2. 收尾清理：删掉因此留下的空行、悬挂标点、空括号、空列表项，不留任何“已清理”“已忽略”痕迹。
3. 三道防线：
   - 生成前：提示词不再诱发这类表述；
   - 生成中：前端流式渲染每帧都过一遍 stripMetaTalk，避免等整句话写完才清理、先说出口再消失；
   - 生成后：写入答案缓存前清理（缓存会原样回放给下一个人，不清理就会被反复发出去）。
4. 幂等：清理两遍结果不变；前后端同一组用例输出完全一致。

五、测试（全部本地实跑）
- 证据裁决 10/10：裁决生效（来源只剩被认可的文件）、被裁文件写入 debug、只调一次、
  全判否仍保留一条、服务报错回退原排序、格式跑偏回退、单条候选不发请求、文件级去重生效。
- 元话语清理 7/7：含括注式、整句式、网站真伪说明、链接有效性说明；有用括注未被误删；幂等通过。
- 前后端一致性 7/7：从 app.js 抽出函数与后端逐条对比，输出完全相同。
- 缓存链路 5/5：脏回答写入缓存前已清理，二次请求命中缓存后回放依然干净。
- 并发验证：judge@24ms 与 search@25ms 同时发起，总耗时 277ms，未被叠加。
- 回归：检索基准 84%/96%/MRR 0.898/2.8ms（与上轮持平）；模糊测试 383 条 0 异常；
  端到端 11/11；热门问题链接 10/10。

六、可调参数
- 裁决触发：候选按文件去重后 ≥2；超时 2600ms；max_tokens 60；输入片段 420 字/份；最多 4 份
- 全判否策略：保留第 1 条（judgeEvidence 内 keep.add(0)）

2026-10-30 第五轮：按 10 条热门卡片逐条实测，修 4 个排序缺陷

一、怎么测的
把 index.html 里 10 条热门提问原样抽出来，走真实后端 /api/ai/ask，每条跑 3 遍。
模型输出层用占位文本替代（本机无密钥），检索、裁决、来源、依据强度全部是真实代码算出来的。
同 IP 连问 30 次会触发既有软限流（30 次/分钟），测试里给每次请求带独立 IP 头绕开。

二、实测暴露的 4 个问题
1. 问“转专业需要满足什么条件”，排第一的是《本科教学质量监控与保障体系纲要》（rel 0.69），
   真正的《转专业及大类专业分流管理办法》只有 0.54。
   看片段才发现：纲要里根本没有“转专业”三个字，它是靠“满足”“条件”两个空词
   外加一条错误的同义词映射（转专业→学籍异动）凑出的 0.74 覆盖率。
2. 问“困难认定要哪些材料”，《国家助学金办法》（0.96）排在《家庭经济困难学生认定办法》前面——
   助学金办法里确实有一段讲认定，但学生要的是认定办法本身。
3. 问“学位绩点要求”，《培养方案指导意见》（0.83）跟《学士学位授予实施细则》几乎并列。
4. 问“期末因病缓考”，参考文件挂了 3 份（考试/学籍/学生管理规定），后两份是顺带提到。

三、改了什么（workes.js，只动检索层）
1. 删掉“转专业→学籍异动”这条同义映射：它会把整本学籍管理召回，而学籍异动是更大的筐。
2. 空动词不入覆盖率：满足、符合、达到、具备、相关、有关、进行、按照、根据、通过
   加入 KB_STOP_TERMS。它们出现与否不改变“这份文件讲不讲这件事”。
3. 标题匹配改成“片段基本都对上”才算命中：
   长词拆成二字比对，“心理咨询”在《…心理…功能室管理制度》里只能对上“心理”，
   半截命中不算——这类文件只是同一领域，不是讲这件事。
   同时标题词表不再只按价值取前五（会被“学金和国”这种跨词碎片占满），
   改为“价值前 4 + 库内常见前 3”，保证“国家奖学金”这类主题词能进比对。
4. 标题命中的文件分层排在前面（tier），没命中的降一档并封顶 rel≤0.55；
   若全场没有任何文件标题命中（如“缺课多少会被取消考试资格”），封顶自动撤销，
   否则正确答案也会被压到 0.55、置信度被误判成“依据有限”。
5. 把文件级 rel 同步回片段：原来上层用片段 rel 决定“这份文件要不要出现在参考文件里”，
   文档级的降权只影响排序、不影响展示，等于白算。
6. 标题加成只做乘法不加固定值：加固定值会把好几份文件一起顶到 1.00，
   1.00 和 1.00 之间没有区别，置信度判断随之失效。
